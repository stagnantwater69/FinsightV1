## P1 findings, fixed locally

### 1. Deleting an in-flight scan can lose the race with external provider dispatch

[`receiptPurge.service.ts`](../../backend/src/services/receiptPurge.service.ts#L155) accepts deletion of a pending scan and later clears its processing lease while setting `Deletion Pending`. The receipt worker can continue through local parsing and call provider rescue before it checks whether that lease was lost in [`receiptScan/worker.ts`](../../backend/src/services/receiptScan/worker.ts#L459).

Provider reservation checks the receipt ID and business profile in [`receiptProviderDispatch.service.ts`](../../backend/src/services/receiptProviderDispatch.service.ts#L278), and the final submission transaction rechecks consent and reservation state at [line 640](../../backend/src/services/receiptProviderDispatch.service.ts#L640). Neither check requires an undeleted `Pending` and `Processing` scan owned by the expected worker lease. If deletion wins after a heartbeat but before dispatch, the adapter can still receive the receipt bytes.

Required correction:

- Revalidate deletion state, confirmation and processing state, delete-purge absence, and expected worker ownership atomically immediately before a dispatch becomes submitted.
- Serialize that check with scan deletion so the winning operation is unambiguous.
- Add a concurrency test where deletion happens between local extraction and provider submission.

**Follow-up status:** Fixed and locally verified.

[`receiptProviderDispatch.service.ts`](../../backend/src/services/receiptProviderDispatch.service.ts) now requires the exact processing lease and locks the receipt row before the final dispatch-state transition. The same transaction rejects scans that are no longer pending and processing, have an evidence-deletion request or `DELETE_SCAN` purge, or no longer belong to that worker attempt. [`receiptScan/worker.ts`](../../backend/src/services/receiptScan/worker.ts) supplies the claimed worker ID and attempt. [`receiptProviderDispatch.test.ts`](../../backend/tests/integration/receiptProviderDispatch.test.ts) covers deletion committed after reservation but before submission, plus stale and lost leases. The adapter receives zero calls, the reservation becomes `CANCELLED`, and reserved and used units return to zero.

### 2. A crash on the final purge attempt can strand the deletion forever

The purge claim predicate in [`receiptPurge.service.ts`](../../backend/src/services/receiptPurge.service.ts#L382) selects only jobs below the ten-attempt ceiling, then increments the attempt during the claim. A job claimed for attempt ten that loses its worker before `recordFailure` remains `PROCESSING` with attempt count ten. It is no longer claimable, and the stalled count at [line 691](../../backend/src/services/receiptPurge.service.ts#L691) sees only explicit `FAILED` rows.

Required correction:

- Terminalize stale max-attempt `PROCESSING` jobs, or allow one atomic stale reclaim that terminalizes them.
- Include the crash-stranded state in operational readiness.
- Add a test that stops after the tenth claim and verifies a bounded terminal outcome.

**Follow-up status:** Fixed and locally verified.

[`receiptPurge.service.ts`](../../backend/src/services/receiptPurge.service.ts) terminalizes stale attempt-ten `PROCESSING` jobs and max-attempt `PENDING` or `RETRY` jobs as `FAILED` with `PURGE_ATTEMPTS_EXHAUSTED`. The readiness count includes those stranded states while preserving a final attempt whose heartbeat is still fresh. [`phase2ReceiptAcceptance.test.ts`](../../backend/tests/integration/phase2ReceiptAcceptance.test.ts) covers the tenth-claim crash, both queued max-attempt states, readiness before and after terminalization, and the fresh-lease exception.

### 3. Mobile `Choose another receipt` leaves capture disabled

Accepted, [batched](../../mobile/src/screens/records/ScanReceiptScreen.tsx#L774), and [resumed](../../mobile/src/screens/records/ScanReceiptScreen.tsx#L941) scans set `scanStarted`, including the accepted path in [`ScanReceiptScreen.tsx`](../../mobile/src/screens/records/ScanReceiptScreen.tsx#L645). The foreign-currency action at [line 2282](../../mobile/src/screens/records/ScanReceiptScreen.tsx#L2282) clears the visible scan and pages but does not clear that guard or the related batch and attempt state. Gallery input and camera opening then return early at [lines 507](../../mobile/src/screens/records/ScanReceiptScreen.tsx#L507) and [1102](../../mobile/src/screens/records/ScanReceiptScreen.tsx#L1102). The capture UI reappears, but its input actions silently do nothing.

Required correction:

- Route this action through the complete scan reset and cleanup path.
- Cover single, batch, and resumed foreign-currency scans in render tests.

**Follow-up status:** Fixed and locally verified.

[`ScanReceiptScreen.tsx`](../../mobile/src/screens/records/ScanReceiptScreen.tsx) routes `Choose another receipt` through one complete reset that cancels active work and clears scan, page, batch, replay-attempt, recovery, duplicate-review, and `scanStarted` state. [`receiptImportFlow.test.tsx`](../../mobile/tests/render/receiptImportFlow.test.tsx) proves that single, batched, and resumed foreign-currency results can immediately start a new upload with a fresh identity and no old batch binding.

### 4. An earlier applied revision of the Phase 2 migration is treated as current

The current [`20260913100918` migration](../../backend/prisma/migrations/20260913100918_receipt_capture_batches_and_scan_revision/migration.sql#L63) creates `ReceiptDuplicateCandidate`, but the disposable local test database records the same migration name with an earlier checksum, `a0e4f79275cbb0e975f16d4675776ecf954395eaa6dd5900f15cd3f73030ca5b`. The tracked file has SHA-256 `8e03ef8f26dba6af0316d4a6488468afecf4a4bb25a972989a8e7a5dda4f782b`. A read-only database-to-schema diff shows that the earlier database lacks the duplicate table and enums, purge mode, evidence-deletion and semantic-fingerprint fields, history indexes, and other current migration objects. Prisma's datamodel diff cannot prove raw-SQL checks, partial indexes, RLS, or revokes, so the missing-object inventory must also cover those controls. The two later migrations do not reconcile this drift.

`prisma migrate deploy` reports no pending migrations because the name is already present. FinSight's startup guard also selects applied migrations by name and completion state without comparing their checksums in [`migrationGuard.ts`](../../backend/src/config/migrationGuard.ts#L49), then reports success at [line 146](../../backend/src/config/migrationGuard.ts#L146). The worker reaches the missing table while completing receipt processing in [`worker.ts`](../../backend/src/services/receiptScan/worker.ts#L302), so an affected environment can boot as healthy and fail its receipt workflow later.

Fresh databases created from commit `28394be` receive the current migration and pass the backend suite. This repository evidence does not establish which revision is installed on hosted Supabase; that requires separately authorized, read-only checksum and schema verification.

Required correction:

- Do not rewrite an applied migration or its ledger row. Inventory the complete schema delta and add a new forward-only reconciliation migration for databases that received the earlier revision.
- Make deployment and startup checks detect unsanctioned checksum drift and verify the required schema shape. If the earlier checksum is explicitly supported, require the reconciliation migration and schema proof before accepting it.
- Test both a fresh migration chain and an upgrade fixture representing the earlier applied shape.

**Follow-up status:** Fixed and locally verified.

The forward-only migration [`20260913230000_reconcile_phase2_scanner_migration_drift`](../../backend/prisma/migrations/20260913230000_reconcile_phase2_scanner_migration_drift/migration.sql) is frozen at SHA-256 `d2f4805aef790c484fd1878edecfcba0a39b93529cb8d9b0879469e2aaa99d46`. It accepts the current source checksum as a verification-only path, repairs only the exact known legacy shape, and rejects unknown checksums, malformed legacy state, altered constraint or index semantics, and unexpected partial Phase 2 objects. [`migrationGuard.ts`](../../backend/src/config/migrationGuard.ts) compares recorded checksums and proves the expected CHECK bodies, foreign-key ownership mappings, index keys, predicates, collations, operator classes, and security controls before startup. It continues without a verdict only for classified transient database unavailability; missing migration assets and ledger or catalog inspection failures refuse startup. [`migrationGuard.test.ts`](../../backend/tests/unit/migrationGuard.test.ts) and [`phase2ReceiptAcceptance.test.ts`](../../backend/tests/integration/phase2ReceiptAcceptance.test.ts) cover the boot verdicts and live malformed catalog cases.

Fresh and supported-legacy disposable databases both report no Prisma schema difference after reconciliation. On the P1 snapshot their 235-fact canonical Phase 2 catalog and security digests were identical at `5b9fbff1a7f8d9aeb3ca15ebdf484e5078d81ec4541cde9fc716ced4a45e39d3`; after the P2-5 `lastActivityAt` column and sweep index were added, both paths produce an identical 237-fact catalog at `eb4d357dd91fe66da9f52557dc500b9b6859ed5da9a8f48deedbea886d9c8c50`. The untracked, not yet committed [`verify-phase2-reconciliation.ts`](../../backend/scripts/migrate-workflow/verify-phase2-reconciliation.ts) harness reconstructs both catalogs and executes the migration against local PostgreSQL. It verifies Prisma parity and the startup guard, rejects a weakened legacy CHECK with no partial repair, and rejects altered active-purge predicates, index collations, and operator classes. No applied migration or ledger row was rewritten outside disposable test fixtures.

## P2 findings

### 5. Seven-day abandoned-scan cleanup is missing

The plan requires deletion seven days after last activity in [`COST-FIRST-CORE-FEATURES-IMPLEMENTATION-PLAN.md`](../COST-FIRST-CORE-FEATURES-IMPLEMENTATION-PLAN.md#L752). `ABANDONED_SCAN` exists as a reason, but [`ReceiptScan`](../../backend/prisma/schema.prisma#L863) has no last-activity field and [`worker.ts`](../../backend/src/worker.ts#L65) schedules no abandoned-scan sweep.

Add indexed last-activity state, update it on owner and worker activity, enqueue idempotent abandoned-scan purges, and test the seven-day clock boundary.

### 6. Confirmation can return an error after financial records commit

The confirmation transaction commits before deferred effects run in [`reconciliation.ts`](../../backend/src/services/receiptScan/reconciliation.ts#L478). Those effects are awaited without isolation at [line 502](../../backend/src/services/receiptScan/reconciliation.ts#L502). A notification write from [`expenseRecord.service.ts`](../../backend/src/services/expenseRecord.service.ts#L246) can therefore produce an HTTP 500 after the records already exist.

Use a transactional outbox, or isolate noncritical post-commit effects and return the committed result. Add failure injection for notifications, analysis queueing, and confirmation feedback.

### 7. Mixed confirmation payload modes are accepted and partly ignored

[`confirmSchema`](../../backend/src/controllers/receiptScan.controller.ts#L148) makes `splits`, `itemAssignments`, `additionalItems`, and `reconciliation` independently optional. The service chooses the item path when `itemAssignments` is present and otherwise chooses `splits` in [`reconciliation.ts`](../../backend/src/services/receiptScan/reconciliation.ts#L384). Valid fields from the other mode can be silently discarded.

Use an exact discriminated or XOR union and reject mixed-mode requests at the controller boundary.

### 8. Duplicate candidate handling is not bounded by its pagination contract

Candidate discovery uses unbounded reads in [`receiptDuplicate.service.ts`](../../backend/src/services/receiptDuplicate.service.ts#L210). Persistence performs a linear search and sequential write for each candidate at [line 319](../../backend/src/services/receiptDuplicate.service.ts#L319). The list endpoint loads the entire candidate set before slicing it at [line 506](../../backend/src/services/receiptDuplicate.service.ts#L506). These operations also run inside bounded OCR and confirmation transactions.

Use database cursor pagination and counting, map existing candidates by key, bulk-write changes, and define a tested oversized-set limit.

### 9. Mobile evidence-page switching can leave a permanent loading veil

[`ReceiptEvidenceViewer.tsx`](../../mobile/src/screens/records/scanReceipt/ReceiptEvidenceViewer.tsx#L78) uses one loading boolean across stored-image requests. When a request is made inactive during a page switch, its cleanup does not clear that flag. Returning to a cached or failed key exits early, leaving the overlay at [line 221](../../mobile/src/screens/records/scanReceipt/ReceiptEvidenceViewer.tsx#L221) visible indefinitely.

Track loading by evidence key or clear it on every key transition. Add a deferred-request switch-away and switch-back test.

### 10. Web recovery history hides scans beyond its first page

[`ScanReceipt.tsx`](../../web/src/pages/ScanReceipt.tsx#L315) requests twenty active scans and discards `nextCursor`. The recovery interface has no pagination. After more than twenty unfinished scans, older entries cannot be resumed or deleted from the web client.

Implement cursor pagination or load-more behavior and test multiple result pages.

### 11. Newly abandoned web scans do not enter recovery history until reload

Active history loads on mount or profile change in [`ScanReceipt.tsx`](../../web/src/pages/ScanReceipt.tsx#L310). `handleRescan` at [line 1029](../../web/src/pages/ScanReceipt.tsx#L1029) clears newly accepted scan and batch references without refreshing that history. The server-side pending scan disappears from the current recovery interface until the route remounts.

Refresh active history after the reset and preserve a visible retry path if that refresh fails.

### 12. Repeated web recovery actions have ambiguous accessible names

Recovery rows in [`ScanReceipt.tsx`](../../web/src/pages/ScanReceipt.tsx#L1358) repeat names such as `Review result` and `Delete scan` without receipt context. Screen-reader button navigation cannot distinguish which row each action controls.

Add contextual accessible names or descriptions and assert them with multiple rows in component or end-to-end coverage.

### Lower-priority items surfaced during the P2 work

These are outside the eight findings and remain open:

- **P3, backend-api:** `createExpenseRecord` in [`expenseRecord.service.ts`](../../backend/src/services/expenseRecord.service.ts) (manual entry) awaits its post-commit `runSideEffects` without the isolation added for receipt confirmation, so the same class of error-after-commit exists there. Within one record's `runSideEffects` thunk, a notification failure still skips that record's analysis enqueue (the daily enqueue backstops it).
- **P3, database and backend-api:** duplicate-candidate scan discovery is one `OR` with an `EXISTS` branch; the no-match case walks the whole profile's scans (6 ms at 5,000 scans). Restructure into index-served branches only if per-profile scan counts grow into the tens of thousands.
- **Operational note, database:** the P2-5 migration's backfill rewrites every `ReceiptScan` row once, and pre-migration owner views were never recorded, so a pending scan the owner merely viewed before the migration is treated as inactive from its last recorded timestamp. Consider observing the first sweep's counts before relying on it in a real-owner project.

## Residual acceptance risks

- Android instrumentation uses synthetic evidence and does not close low-memory, permission, background, thermal, TalkBack, rotation, crop, or real-receipt behavior.
- Native capture maps preview-analysis corners onto a later still image. Movement and device-specific CameraX behavior remain physical-device risks.
- Hosted grants, default ACLs, private Storage policies, backups, and the partial hosted migration remain unverified. The three accidental SELECT-only probes do not close those checks.
- Cloud OCR remains disabled. The provider deletion race now has deterministic local regression coverage, but hosted enablement still requires separately authorized deployment and operational verification.
- Duplicate-set handling is now bounded at 200 candidates with database-side pagination, measured on a 212,002-scan seeded database; hosted load behavior is still unmeasured.
